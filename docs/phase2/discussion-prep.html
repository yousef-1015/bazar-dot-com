2. Phase 1 Summary

Phase 1Architecture
Explain Phase 1 in 30 seconds.
Phase 1 built a simple three-service microservice system. The client only talks to the frontend on port 3000. The frontend forwards lookup requests to the catalog service on port 3001 and purchase requests to the order service on port 3002. The catalog stores book data in a CSV file. The order server checks stock through catalog, decrements stock through catalog, then appends a row to its order CSV.

Phase 1Docker
What did Docker do in Phase 1?
Each service has a Dockerfile. Docker Compose starts the frontend, catalog, and order containers on one internal Docker network. The frontend uses Docker service names like http://catalog:3001 instead of localhost because inside a container, localhost means the same container, not the other service. CSV files are mounted as volumes so data changes persist outside the container.

3. Phase 2 Summary

Phase 2Architecture
Explain Phase 2 in 45 seconds.
Phase 2 adds replication, caching, and consistency. Catalog has two replicas on ports 3001 and 3003. Order has two replicas on ports 3002 and 3004. The frontend is still single and runs on port 3000. The frontend uses per-request round-robin load balancing to choose a replica. It also has an in-memory cache for GET /info/:id. When catalog data changes, catalog sends DELETE /cache/:id to the frontend before writing, so stale book info is removed. Replicas use POST /sync to mirror writes.

Phase 2Performance
How did we measure performance?
We used curl -w "%{time_total}" to measure total response time through the frontend. We ran 20 requests and averaged them. We measured cached GET /info/1, cache miss after deleting the cached item, and the invalidation request itself with DELETE /cache/1. Results were documented in docs/phase2/performance-results.md.
for i in {1..20}; do curl -s -o /dev/null -w "%{time_total}\n" http://localhost:3000/info/1 done

5. Likely Discussion Questions

Q1Overview
Explain the project generally.
We implemented Bazar.com as a microservice system. Phase 1 had frontend, catalog, and order services. The frontend is the only service clients call. Catalog stores book data in CSV and supports search, info, and update. Order handles purchases by checking catalog stock, updating quantity, and writing orders to CSV. Phase 2 added replicas, round-robin load balancing in the frontend, an in-memory cache for book info, cache invalidation for consistency, and sync endpoints to keep replicas consistent.
Q2Load Balancing
What algorithm did you use for load balancing?
We used per-request round-robin. The frontend keeps an array of replicas and an index. For each request, it picks the current URL, increments the index modulo the number of replicas, and forwards the request. Catalog requests rotate between catalog and catalog-replica. Order requests rotate between order and order-replica.
Q3Caching
What exactly did you cache and why?
We cache only successful GET /info/:id responses. This endpoint returns lookup data for a single book, so it is useful to reuse. We do not cache POST /purchase/:id because purchases are writes. We also do not cache failed catalog responses because the frontend only stores data if response.ok is true.
Q4Consistency
How do you keep the cache consistent?
We use server-push invalidation. Before catalog writes a changed book to its CSV, it calls the frontend endpoint DELETE /cache/:id. The frontend deletes that one cached item. After the write, catalog syncs the update to the other catalog replica. This prevents the frontend from serving stale book info after a purchase or catalog update.
Q5Replica Sync
How do replicas stay consistent?
Each replica has a POST /sync endpoint. When one catalog replica updates price or quantity, it writes locally and calls POST /sync on the other catalog replica. The sync endpoint applies the same update but does not sync back, which avoids an infinite loop. Order replicas do the same for new order rows.
Q6Docker
What did you write in Docker Compose and what are the ports?
Docker Compose defines five services: frontend on 3000, catalog on 3001, catalog-replica on 3003, order on 3002, and order-replica on 3004. All are on the same Docker network. Inside Docker, services use hostnames like catalog, catalog-replica, order, and order-replica. CSV files are mounted as volumes so data persists.
Q7Performance
How did you measure performance?
We used curl's time_total output and ran 20 requests for each experiment. We measured cached info lookup, cache miss after invalidation, and invalidation request overhead. The results are in docs/phase2/performance-results.md. Because everything ran locally in Docker, all times were very small.
Q8Tradeoffs
What are the main tradeoffs or limitations?
Round-robin is simple but does not know which replica is healthier or less busy. The in-memory cache is fast but disappears if the frontend restarts. CSV files are easy for the lab, but they are not ideal for concurrent writes or transactions. Improvements would include health checks, retries, a real database, locks or transactions, cache size limits, and an LRU cache policy.
